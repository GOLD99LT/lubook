# 嵌入式 Linux 全景：从 SoC 上电到应用启动

> 本章是全书导读：说明这本手册解决什么问题、怎么读、与其他分册的关系。
> 具体章节的定量结论与来源在各章正文内给出。

## 这本手册要解决什么问题

嵌入式 Linux 的门槛不在"会写驱动"，而在**整条启动链的可见性**：
SoC 上电后做了什么、U-Boot 把控制权交给谁、内核怎么找到设备树、
驱动为什么没 probe、用户空间为什么起不来。这些环节任何一处出错，
现象都只是"板子没反应"或"串口没输出"。

本手册按"启动链 → 设备树 → 驱动模型 → 用户空间 → 升级与可靠性"组织，
每章都给出可以在真实板子上复现的最小验证步骤。

## 学习路径

| 阶段 | 内容 | 产出 |
|---|---|---|
| 第一篇 | 交叉编译、构建系统、启动流程 | 能从零构建一个可启动镜像 |
| 第二篇 | 内核模块、字符设备、platform 驱动、设备树绑定 | 能写一个可加载、可热插拔的驱动 |
| 第三篇 | systemd、网络、调试与性能分析 | 能定位用户空间启动失败与性能瓶颈 |
| 第四篇 | I2C/SPI/显示/音频等板级接口 | 能把外设接进系统 |
| 第五篇 | 看门狗、日志、A/B 升级、安全启动 | 能做可量产升级方案 |
| 第六篇 | 板级 bring-up 实战 | 能独立完成一块新板的软件适配 |

## 与 MCU 分册的区别

MCU 分册关注"寄存器级控制与实时性"；本分册关注"操作系统提供的抽象与整机集成"。
两者共同点是：**都要对照硬件时序与数据手册**，而不是只调用 API。

## 自测

<details><summary>为什么嵌入式 Linux 要先学启动链，而不是先学写驱动？</summary>
因为驱动没 probe 的原因，八成不在驱动代码里——可能是设备树节点没使能、
时钟/电源域没打开、pinctrl 复用没配对。不理解启动链与设备树，
就只能靠"改一行、重启、看串口"的盲试。
</details>

<details><summary>A/B 升级为什么比"覆盖写入"更可靠？</summary>
覆盖写入在掉电时会留下半个镜像，设备直接变砖；A/B 双分区保证任何时刻至少有一份完整可启动镜像，
失败可以回滚。代价是需要双倍存储与一次重启。
</details>
