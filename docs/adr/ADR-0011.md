# ADR-0011：构建内存预算——内容规模增长后必须显式抬高 Node 堆

- 状态：Accepted
- 日期：2026-10-23
- 相关：ADR-0001（技术栈）、ADR-0004（双形态共用 manifest）

## 背景

内容深化到第 15 批（practice 篇收官）时，`pnpm build:hardware` 突然失败：

```text
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
[ELIFECYCLE] Command failed with exit code 134.
```

失败原因不是某个文件有语法错，而是**站点规模本身**：

| 指标 | 数值（2026-10-23 实测） |
|---|---|
| Markdown 文件 | 143 个 |
| Markdown 总量 | 4.57 MB |
| 正文字数 | 约 76 万字（深化前约 18 万字） |

VitePress 的构建（客户端 bundle + 服务端 SSR + MiniSearch 全文索引 + 每页 KaTeX 渲染）
需要把全部内容同时放进内存。Node 在该机器（15.4 GB RAM）上默认堆上限约 4 GB，
不足以完成一次构建。

**这不是"机器太差"**：同一份内容在 GitHub Actions 的 16 GB runner 上同样会 OOM，
只是阈值更高一点。也就是说，这是内容规模与构建内存之间**结构性**的冲突，
会随内容继续增长而反复出现，必须在配置层明确下来，而不是每次靠"再跑一次"。

## 决策

1. **在 `.npmrc` 里声明 `node-options`**，让所有 lifecycle script 都带上堆参数：

   ```ini
   node-options=--max-old-space-size=6144
   ```

   选 `.npmrc` 而不是改 `package.json` 脚本，是因为它是**唯一跨平台**的注入点：
   `package.json` 里写 `NODE_OPTIONS=... vitepress build` 在 Windows 的 cmd/pwsh 下不生效，
   而引入 `cross-env` 会为一个环境变量新增一个依赖。

2. **值取 6144 MB（6 GB）**：实测 4 GB 失败、6 GB 成功（构建耗时 111 s）。
   在没有实测依据前不要往小调；调大要考虑 CI runner 的物理内存（ubuntu-latest 为 16 GB）。

3. **CI 不额外配置**：`quality.yml` / `deploy-docs.yml` 都通过 `pnpm` 执行构建，
   因此自动继承 `.npmrc` 的 `node-options`。若将来有 workflow 直接调 `vitepress` 或 `node`，
   必须在该 step 显式设置 `NODE_OPTIONS`。

4. **这条约束纳入验收**：`pnpm verify:all` 里包含 `build:hardware`，
   所以内存不足会以 `hardware:build` 失败的形式暴露，不会被静默吞掉。

## 后果

- 本地与 CI 行为一致，构建不再因内存随机失败。
- 代价：构建峰值内存约 6 GB。对开发机是要求（≥8 GB 可用），对 CI 是常态资源。
- **若内容继续增长到约 6 MB Markdown 以上**，需要重新评估本 ADR：
  可选方向是拆站（按篇分册构建）、关闭全站搜索索引改用外部搜索、
  或把 KaTeX 从构建期预渲染改为运行期渲染。这三条都会改变 ADR-0004 的对账口径，
  届时应新增 ADR 而不是直接调大数值。
