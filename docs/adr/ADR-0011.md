# ADR-0011：构建内存预算——内容规模增长后必须显式抬高 Node 堆

- 状态：Accepted
- 日期：2026-10-23
- 相关：ADR-0001（技术栈）、ADR-0004（双形态共用 manifest）

## 背景

内容深化到第 15 批（practice 篇收官）时，`pnpm build:hardware` 突然失败：

```text
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
[ELIFECYCLE] Command failed with exit code 134.
```

失败原因不是某个文件有语法错，而是**站点规模本身**：

| 指标 | 数值（2026-10-23 实测） |
|---|---|
| Markdown 文件 | 143 个 |
| Markdown 总量 | 4.57 MB |
| 正文字数 | 约 76 万字（深化前约 18 万字） |

VitePress 的构建（客户端 bundle + 服务端 SSR + MiniSearch 全文索引 + 每页 KaTeX 渲染）
需要把全部内容同时放进内存。Node 在该机器（15.4 GB RAM）上默认堆上限约 4 GB，
不足以完成一次构建。

**这不是"机器太差"**：同一份内容在 GitHub Actions 的 16 GB runner 上同样会 OOM，
只是阈值更高一点。也就是说，这是内容规模与构建内存之间**结构性**的冲突，
会随内容继续增长而反复出现，必须在配置层明确下来，而不是每次靠"再跑一次"。

## 决策

1. **构建入口自己抬堆：`packages/tooling/bin/vitepress-with-heap.mjs`。**
   `apps/hardware` 的 `docs:build` 改为调用这个包装器，它用
   `node --max-old-space-size=8192 <vitepress cli>` 重新起进程。

   为什么不用更省事的写法（都试过并失败）：

   | 方案 | 结果 |
   |---|---|
   | `.npmrc` 里写 `node-options=--max-old-space-size=...` | **无效**。实测 `pnpm exec node -p process.env.NODE_OPTIONS` 为 `UNSET`，堆上限仍是默认 4288 MB |
   | `package.json` 写 `NODE_OPTIONS=... vitepress build` | Windows 的 cmd/pwsh 不认这种前缀赋值 |
   | 引入 `cross-env` | 为一行环境变量新增依赖，且只解决本地、不解决其他入口 |

   包装器是零依赖、跨平台、且对**任何**调用方都生效（`pnpm build:hardware`、
   `pnpm bundle:pages`、`verify_all.py`、CI 的 build step），
   所以它是唯一能把"本地通过 = CI 通过"真正对齐的做法。

2. **值取 8192 MB（8 GB）**：这不是一次拍定，而是两次实测撞出来的——
   正文 122 章、约 4.57 MB 时 4 GB 失败、6 GB 通过（111 s）；
   补完附录与题库（约 4.8 MB）后 **6 GB 也失败**，8 GB 才通过（116 s）。
   结论：**峰值落在 6~8 GB 之间，且随内容单调增长**；没有实测依据前不要往小调。
   调大要考虑机器与 CI runner 的物理内存（ubuntu-latest 16 GB，够用）。

3. **CI 双保险**：`quality.yml` 的 build job 与 `deploy-docs.yml` 在 job / workflow 级显式设
   `NODE_OPTIONS: --max-old-space-size=8192`。包装器已经生效，但这两个 workflow
   历史上曾连续两次失败（先 quality/build，再 deploy 的 `bundle:pages`——
   后者会带 `VP_BASE=/lubook/` 整体重建一遍），显式设置成本极低，留作冗余。
4. **CI 失败必须可诊断**：Actions 日志需要凭证才能读，因此 build step 在失败时
   把日志尾部写成 `::error::` annotation，可由 `/commits/<sha>/check-runs` 的
   annotations 接口匿名读取。
5. **这条约束纳入验收**：`pnpm verify:all` 里包含 `build:hardware`，
   所以内存不足会以 `hardware:build` 失败的形式暴露，不会被静默吞掉。

## 后果

- 本地与 CI 行为一致，构建不再因内存随机失败。
- 代价：构建峰值内存 6~8 GB。对开发机是要求（≥10 GB 可用），对 CI 是常态资源。
- **本 ADR 的余量已经不多了**：4.57 MB 时 6 GB 够、4.8 MB 时 6 GB 就不够了——
  也就是说每增加约 0.2 MB Markdown，峰值可能上一个台阶。
  **再增长到约 5.5~6 MB 必须重新评估**：可选方向是拆站（按篇分册构建）、
  关闭全站本地搜索索引改用外部搜索、或把 KaTeX 从构建期预渲染改为运行期渲染。
  这三条都会改变 ADR-0004 的对账口径，届时应新增 ADR 而不是继续调大数值。
