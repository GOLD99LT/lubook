# ADR-0012：数学渲染改为运行期（构建内存降 61%，HTML 降 71%）

- 状态：Accepted
- 日期：2026-10-23
- 相关：ADR-0011（构建内存预算）、ADR-0010（客户端包体预算）、ADR-0004（双形态共用 manifest）

## 背景

ADR-0011 只回答了"要多少内存"，没回答"内存花在哪"。补测三组对照后拿到了归因：

| 配置 | 页面数 | 峰值内存 | 耗时 | 产物 HTML |
|---|---:|---:|---:|---:|
| 现状（构建期 KaTeX + 本地搜索） | 144 | 5.94 GB | 110 s | 80.1 MB |
| 关闭本地搜索 | 144 | 5.46 GB | 88 s | — |
| **不渲染 KaTeX（只留公式源码）** | 144 | **2.14 GB** | **41 s** | **21.9 MB** |
| 只构建 basics 篇（构建期 KaTeX） | 18 | 1.76 GB | 35 s | — |

结论很明确：**构建期渲染 40,146 个公式片段，占了峰值内存的约 64%（3.8 GB）和 69 秒**；
本地搜索只占 0.48 GB（8%）。产物 HTML 里 KaTeX 标记占 **36%（27.8 MB / 76.8 MB）**，
而内联 SVG 只有 1.1 MB（1%）。

也就是说，"内容太多"不是主因，**"在构建期把每个公式渲染成 DOM"才是**。
这是一个设计选择，可以换。

## 决策

**数学公式改为运行期渲染**：

1. `@lubook/shared-config` 的 markdown 管线注册的数学渲染器改为只输出占位：
   ```html
   <span class="math-tex math-tex--inline" data-math="TeX 源码">TeX 源码</span>
   ```
   占位内保留源码，作为"JS 未执行/加载失败"时的降级显示（可读，只是没排版）。
   设 `LUBOOK_MATH=build` 可退回构建期渲染，仅用于对照测量。
2. `@lubook/theme` 增加运行期渲染器：首次渲染后 `import('katex')`（懒加载，独立 255 KB chunk，
   浏览器缓存一次），用 `katex.renderToString` 填充占位并标记 `data-rendered`；
   客户端路由切换用 MutationObserver 兜住，不依赖路由钩子。
3. 占位期间用等宽字体显示源码（`packages/theme/src/style.css`），避免空白闪烁；
   渲染完成后该样式自动失效。
4. KaTeX 的 CSS 与字体仍由主题静态引入——排版要用，且体积由浏览器缓存。

## 效果（同一份内容，实测）

| 指标 | 构建期渲染 | 运行期渲染 | 变化 |
|---|---:|---:|---:|
| 构建峰值内存 | 5.94 GB | **2.30 GB** | −61% |
| 构建耗时 | 110 s | **45 s** | −59% |
| 产物 HTML 总量 | 80.1 MB | **23.6 MB** | −71% |
| 8 GB 堆可支撑页数 | 约 183 页 | **约 615 页** | +4.3× |
| 首屏新增 | — | 255 KB chunk（懒加载，一次） | +1 次请求 |

浏览器验收：`opamp/noise` 页 568 个占位全部渲染为 KaTeX（1,770 个 `.katex` 元素、
`katex-error` 计数 0）；`quizbank/quiz-opamp` 220 个占位同样全部渲染、0 错误。

## 代价与取舍

- **首屏有一次公式排版跳变（FOUT）**：占位先显示源码，katex 到位后替换。
  缓解：CSS 让源码以等宽小号灰字显示，跳变可控；KaTeX chunk 与页面 chunk 并行加载。
- **SEO**：静态 HTML 里是 TeX 源码而不是排版结果。搜索引擎普遍执行 JS，
  但纯静态抓取会看到 `$...$`。若将来 SEO 成为硬指标，可对爬虫做预渲染（另议）。
- **离线单文件**：本来就由客户端 `katex.render` 渲染，本次改动让两条交付路径口径一致。
- **搜索索引**：索引体积不变（7,038 KB），因为它基于正文文本而非渲染后的 DOM；
  索引里的公式是 TeX 源码，按公式名搜索反而更好命中。

## 备选方案与为什么没选

- **拆站**（按篇拆成 4~6 个 VitePress 构建）：峰值也能降到约 2 GB，但要 6 次串行构建、
  重建全局搜索、按篇切分 sidebar/nav，并冒路由变更风险（ADR-0002 不变量）。
  在运行期渲染已经把容量放大 4.3 倍之后，拆站不再划算；留作 600 页以上时的选项。
- **关本地搜索**：只省 8%，还要牺牲全站搜索，不值。
- **继续加大堆**：治标；且团队机器与 CI 的物理内存不会跟着涨。

## 后果

- ADR-0011 的内存模型随之更新：构建期渲染时是 `1.16 GB + 33 MB/页`，
  现在（运行期渲染）是 **`0.80 GB + 10.4 MB/页`**。
  `build_memory_budget.py` 的常数已同步，并在文件头注明"换渲染策略必须重测"。
- 若将来把 KaTeX 改回构建期渲染（例如为了 SEO），内存会立刻回到 5.9 GB 量级，
  必须同时改回堆配置并重新测量。
