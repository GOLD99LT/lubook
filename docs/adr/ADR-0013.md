# ADR-0013：双站部署拓扑与 CI 并发分组

- 状态：Accepted
- 日期：2026-10-23
- 相关：ADR-0006（品牌与门户）、ADR-0011（构建内存）

## 背景

站点有两条发布路径：

- **主站**：GitHub Pages，`VP_BASE=/lubook/`，地址 `https://gold99lt.github.io/lubook/`；
- **镜像**：Cloudflare Pages（国内访问用），`VP_BASE=/`，地址 `https://lubook.pages.dev/`。

镜像工作流 `deploy-cloudflare.yml` 原本只保留 `workflow_dispatch`（手动触发），
理由是"没配 Cloudflare 凭据前不该让 CI 空转"。

2026-10-23 凭据与 Pages 项目配置完成后，改为 **随 main 自动镜像**（`push: branches: [main]`）。
于是同一个 push 会触发两条流水线，而两条流水线都把 `quality.yml` 当**可复用工作流**当前置门禁
（F05：门禁不绿不许上线）。这就暴露了并发分组的冲突。

## 问题：门禁互相取消（同一 bug 的第二次形态）

`quality.yml` 原本的并发组是：

```yaml
concurrency:
  group: quality-${{ github.ref }}
  cancel-in-progress: true
```

同一个 ref（`refs/heads/main`）下，两条流水线各自调用一次门禁 → 落在同一组 →
`cancel-in-progress: true` 让后到的取消先到的。表现是：

```
Deploy to Cloudflare Pages (mirror)   [success]
Deploy VitePress docs to Pages        [cancelled]   ← 门禁 job 全部 cancelled，deploy 被 skip
```

**这不是第一次**。2026-10-22 首上线时同样的机制取消过一次部署，
当时的处置是"把 main 从 quality.yml 的 push 触发里排除"（让 main 只经由部署流水线调用门禁）。
那个修复解决了当时那一对冲突，但**没有解决根因**——只要有两个调用方，冲突就会再来。

## 决策

1. **并发组把调用方纳入 key**：

   ```yaml
   concurrency:
     group: quality-${{ github.workflow }}-${{ github.ref }}
     cancel-in-progress: true
   ```

   可复用工作流里 `github.workflow` 指向**顶层调用者**，因此
   `Deploy VitePress docs to Pages` 与 `Deploy to Cloudflare Pages (mirror)` 落在不同组，
   互不取消；而同一条流水线的重复推送仍然落在同一组、照旧去重（这是我们想要的）。

2. **两条流水线都跑完整门禁**：镜像站不是"低保证副本"，门禁必须在发布前跑。
   代价是同一次 push 会跑两遍质量门禁，CI 时间约翻倍——这是镜像存在的必要成本。

3. **镜像与主站内容必须一致**：两者都由同一 commit 构建，只有 `VP_BASE` 不同。
   验收方式是 `check_live_site.py` 对两边各跑一遍（路由快照 + 同源资源）。
