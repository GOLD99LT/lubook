# ADR-0007 · 学习数据与离线双形态统一协议（迁移隔离 / 持久化反馈 / 章节 id 唯一）

- 状态：**Accepted（2026-10-22 阶段 A 实施完成，verify:all 全绿；停在分支 `main` 本地，未 push）**
- 日期：2026-10-22
- 关联：[ADR-0003](ADR-0003.md)（学习数据仓储化）、[ADR-0004](ADR-0004.md)（双形态对账）、[ADR-0006](ADR-0006.md)（多 app 门户拓扑）、[ARCHITECTURE.md §14](../../ARCHITECTURE.md)、审查报告 `reviews/PROJECT-REVIEW-2026-10-21.md`（F01/F04/F06/F07/F08/F09）

## 上下文（Context）

独立审查（`reviews/PROJECT-REVIEW-2026-10-21.md`）在学习数据与离线双形态上发现一组会直接造成数据错误或丢失的缺陷：

- **F09 迁移串数据**：`packages/learning/src/index.ts` 启动时把**最早全局键** `hh.v1.learning` **无条件**纳入**每一个 app** 的迁移来源；同时 `knownIds` 从已持久化的历史存储中播种。结果是任何新建分册（未来的 `embedded` / `embedded-linux`）只要浏览器里存在旧全局键，就会把硬件分册的进度/收藏/笔记误当作自己的数据。
- **F04 持久化失败无反馈**：`persist()` 捕获 `setItem` 异常后仅 `console.warn`，写入方法仍返回成功；`ChapterLearning.vue` 一律提示"已保存"。当存储配额耗尽（QuotaExceeded）或被禁用时，用户以为已保存，实际数据在刷新后丢失。
- **F08 在线/离线协议分裂**：在线导出带 `schemaVersion/appId/contentRevision` 的版本化信封；离线单文件页只导出 `{exportedAt, learned, starred, notes}`，且**没有导入流程**。两套字段、两套 id（在线用相对路径、离线用 frontmatter 短 slug），备份互不兼容。
- **F06 离线公式双重转义**：`build_single_html.py` 先对整行 `H.escape`，匹配到 `$...$` 后又对公式内容 `attr_escape`，公式被编码两次，KaTeX 渲染出 102 个 `.katex-error`。
- **F07 离线内部链接失效**：离线页把所有 Markdown 链接原样输出为 `target=_blank`，其中 43 个指向本仓 `.md` 的内部链接在单文件页中无法打开。
- **F01 门户跨 app 导航 404**：门户点硬件卡片走的是 VitePress 客户端路由，跨 app base 边界解析错误，落到 `/lubook/hardware/` 显示 404（整页加载/刷新正常）。

本 ADR 只约束**数据协议、迁移隔离、章节 id、持久化反馈**，并据此指导 F01/F04/F06/F07/F08/F09 的实现。F02/F03/F13 是正文安全勘误，不涉及协议。

## 决策（Decision）

### 1. 版本化导出/导入 schema：在线与离线共用同一信封

唯一的学习数据信封（`LearningExport`，`schemaVersion=1`）：

```json
{
  "schemaVersion": 1,
  "appId": "hardware",
  "contentRevision": "sha256-361225735a3a67f4",
  "exportedAt": "2026-10-22T08:00:00.000Z",
  "progress":  { "<chapterId>": "done | learning" },
  "favorites": { "<chapterId>": true },
  "notes":     { "<chapterId>": { "text": "...", "updatedAt": "ISO-8601" } }
}
```

- `contentRevision` 缺省为 `'unknown'`，导出时可由入参覆盖；`exportedAt` 为导出时刻 ISO-8601。
- **离线单文件页必须导出完全相同的信封**（替代旧的 `{exportedAt, learned, starred, notes}`），并新增**文件选择导入**（`<input type="file">` + `FileReader`），与在线 `HomePanel.vue` 的导入对称。
- 导入校验（在线、离线一致）：
  1. `schemaVersion === 1`，否则拒收；
  2. `appId` 与当前分册一致，否则拒收（避免把别的分册备份导入）；
  3. `progress` 取值只能是 `'done' | 'learning'`，`favorites` 只能是 `boolean`，`notes` 项必须是 `{text:string, updatedAt:string}`；
  4. 笔记大小上限：单条 100,000 字符、总量 5MB；
  5. 章节 id 不在当前已知集合（`knownIds`）内的记录一律落 **tombstone**：不写入、不计完成率，在结果中返回被忽略的 id 列表。
- 导入支持 `merge`（按字段合并，notes 按 `updatedAt` 取新）与 `replace`（整体替换）两种模式；UI 默认 `replace`。

### 2. 迁移来源完全由 app 显式声明（F09）

- **移除** `createLearningRepository` 中把全局 `OLD_KEY='hh.v1.learning'` 无条件前置的逻辑。迁移来源**只**取 `opts.legacyKeys ?? []`，新分册默认空数组 → 不做任何迁移。
- 各分册在自己的 `content.config.ts` 显式声明历史来源（从旧到新）：
  - 硬件分册：`legacyKeys: ['hh.v1.learning', 'hb.v1.handbook.learning']`；
  - 未来 `embedded` / `embedded-linux`：默认不声明，无历史来源。
- 迁移后**旧键保留不删除**（与 ADR-0003 一致）。
- 迁移读取的记录同样要经过 `knownIds` 过滤：历史存储中属于已删除/改名章节的 id 不进入当前状态（不按历史存储播种）。

### 3. knownIds 由 catalog 注入，不按历史存储播种（F09）

- `CreateLearningRepositoryOptions` 新增 `knownIds?: string[]`，由 app 从其 catalog（`catalog.entries[].id`，即相对路径）注入；仓储内部的已知章节集合 = `new Set(opts.knownIds ?? [])`。
- **删除** 启动时从已持久化数据 `seedKnown()` 的逻辑，以及 `getChapter()` 访问即登记为已知的副作用——已知集合是 catalog 的事实，不随存储历史或 UI 临时访问而扩张。
- 迁移、导入时，凡不在 `knownIds` 的 id 一律落 tombstone。
- 硬件分册原先用 `catalog.entries.forEach(e => repository.getChapter(e.id))` 来"补登记"的临时做法，改为直接通过 `knownIds` 注入。

### 4. 章节 id 唯一规则（F08，含旧离线 id 兼容）

- **全局规范章节标识 = `<appId>/<relativePath>`**，例如 `hardware/basics/voltage-current-power.md`。该标识天然跨 app 唯一，未来多个分册即使都含 `intro.md` 也不会冲突。
- **在单个分册的存储键与数据信封内部，记录键使用裸 `relativePath`**（如 `basics/voltage-current-power.md`），因为 `appId` 已由存储键（`lubook.v1.<appId>.learning`）与信封字段固定。在线与离线的**裸键完全一致**，从而保证两种形态的备份可互通。
- **离线单文件页的章节 id 从 frontmatter 短 slug（如 `voltage-current-power`）改为裸 `relativePath`**，与在线 catalog 对齐。
- **旧离线 id → 路径兼容映射**：构建期为每个章节建立 `frontmatter slug → relativePath` 的映射，用于：
  1. 迁移旧离线 localStorage（旧三键 `<prefix>-learned/-starred/-notes`，以短 slug 为键）；
  2. 导入旧版离线备份文件（`{learned, starred, notes}`，以短 slug 为键）。
- **前向兼容**：导入解析对带或不带 `<appId>/` 前缀的键都接受——若键以当前 `appId + '/'` 开头则剥去前缀；其他 app 前缀的键按未知 id 处理。这样未来若信封内出现跨 app 数据，无需再改解析。

### 5. 持久化结果进入仓储接口，成功/失败可感知（F04）

- 内部 `persist()` 不再只 `warn`，而是返回结果并更新一个响应式状态：

  ```ts
  interface PersistResult { ok: boolean; error?: string }
  // 响应式：
  interface SaveState { ok: boolean; error: string | null; updatedAt: string | null }
  ```

- 所有写方法（`setChapter / setStatus / setFavorite / setNote / clearAll`）返回 `PersistResult`；`importData` 只有在 `persist()` 成功后才返回 `ok:true`，持久化失败时返回失败结果。
- 仓储暴露只读响应式 `saveState` 与 `retryPersist()`（用当前内存状态重写一次，供"重试"按钮）。
- 内存中的 reactive 状态在写入失败时仍保留（会话内不丢），UI 据此提示"未保存"，并提供：
  - **重试**（调用 `retryPersist()`）；
  - **立即导出**（即使本地写不进去，也能把数据导出成文件兜底）。
- UI 绝不在 `persist()` 失败时提示"已保存"。

### 6. 离线内部存储统一为单键（F08）

- 离线单文件页从旧的三个分散键（`<storePrefix>-learned/-starred/-notes`，其中 hardware 的 `storePrefix='hh'`）改为与在线一致的**单个组合键** `lubook.v1.<appId>.learning`，内容为 `PersistedShape {schemaVersion, appId, progress, favorites, notes}`。
- 首次加载时若新键不存在，则读取旧三键并经 §4 的 slug→路径映射一次性迁移；旧键保留。
- 由此离线页的进度/收藏/笔记读写、导出、导入、渲染全部复用同一套字段与 id，与在线同构。

### 7. 跨 app 导航边界（F01）

- **跨 app（门户 ↔ 分册）边界使用整页导航**：门户卡片点击用 `location.assign(withBase(slug + '/'))` 触发完整页面加载，不交给 VitePress 客户端路由；"回门户"等其他跨 app 入口同样处理。
- **app 内部章节切换保持 VitePress 客户端路由**（不整页刷新）。
- 判定边界：链接目标改变了 app / base（进入或离开 `<slug>/`）即整页导航；目标仍在当前 app 内即客户端路由。

### 8. 补充：存储不可用诚实反馈与导入模式确认（2026-10-22 遗留缺陷整改）

§5 只覆盖了"存储可写但写失败"；另有一种更隐蔽的失败：`localStorage` 不可访问时仓储静默降级为内存 Storage，其 `setItem` 永远成功，界面仍显示"已保存"。本节补充，不改变 §1 的信封字段与 §2/§3 的迁移隔离规则：

- `SaveState` 增加 `persistent: boolean`。降级为内存 Storage 时 `persistent=false`、`ok=false`，`error` 为"浏览器存储不可用，数据仅保存在当前会话"；读写功能保持可用，仅保存状态如实降级。
- 存储可用性必须实际探测一次读写，不能只看 `globalThis.localStorage` 是否存在；`SecurityError`（隐私模式/策略禁用）降级为内存，`QuotaExceededError` 保留原 Storage 以便 `retryPersist()` 恢复。
- 内存模式下 `persist()` 不再信任 `setItem` 的成功返回；写方法与 `importData` 返回 `ok:false`，导入消息为"已导入到当前会话但未能持久化…"。
- §1 的"UI 默认 `replace`"由本节更新：`HomePanel` 必须先让用户选择 `merge` / `replace`，仓储门面 `importJSON` 默认 `merge`；选择 `replace` 时须 `window.confirm` 明确提示"将覆盖当前全部学习数据且不可撤销"，取消则不执行。
- SSR 构建期没有浏览器存储，保存状态只在 `mounted` 后展示，避免静态 HTML 误报"仅本次会话"或与水合结果冲突。

## 离线内部链接改写（F07，落实 §4）

- 构建期建立"章节相对路径 → 单文件内锚点"映射：每个章节在单文件页中的锚点 = 其裸 `relativePath`（`/` 与 `.` 做锚点安全化处理，保证唯一）。
- 正文 Markdown 链接分类处理：
  - **内部链接**（目标为相对路径 `.md`，含 `../` 上级与 `#xxx` 同页锚点）：改写为单文件内 `#<anchor>` 跳转，不新开窗口；
  - **跨分册目标**（指向本 app 之外、单文件内不存在）：渲染为不可点击的占位文本并标注"目标不在本离线册"，不产生死链；
  - **外部链接**（`http(s)://`、`mailto:` 等）：保留 `target="_blank" rel="noopener"`。

## 离线公式渲染（F06，落实 §1）

- 调整行内处理顺序：先**分词/提取并保护原始 LaTeX**（行内 `$...$`、块级 `$$...$$`，提取的是未经 HTML 转义的原文），再对：
  - 正文文本按 HTML 转义一次；
  - 放入 `data-t` 属性的公式原文按属性转义一次（`attr_escape`）。
- 公式原文只在放入属性时编码一次，正文不再先转义公式，消除双重转义；KaTeX 以 `throwOnError:false` 渲染。

## 验收（Verification）

- `corepack pnpm verify:all` 退出 0；`@lubook/learning` 单测全过（含新增用例）。
- 新增 learning 单测覆盖：
  1. 注入会抛 `QuotaExceededError` 的 Storage，写方法返回 `ok:false`、`saveState.ok===false`，页面不提示已保存；`retryPersist()` 在存储恢复后成功并刷新；
  2. 两个 app 共用同一 Storage 且新 app `legacyKeys` 为空时，新 app 不迁移旧全局键（`done=0 / pct=0`）；
  3. 迁移/导入中未知 id 落 tombstone、不落库、不计完成率。
- 在线分别以 `VP_BASE='/'` 与 `VP_BASE='/lubook/'` 构建，浏览器实测"门户 → 硬件 → 章节 → 回门户"全程点击无 404。
- 重建离线 `dist/hardware.html`，浏览器实测：`.katex-error` 由 102 降为 **0**；指向 `.md` 的内部链接由 43 降为 **0**。
- 存储写失败时不再提示已保存；新建空 `legacyKeys` 的 app 不串硬件数据（`done=0 / pct=0`）。
- 在线与离线各完成一次"写笔记 → 刷新 → 导出 → 清空 → 导入 → 刷新"往返，数据一致。
- 内容勘误（F02/F03/F13）只改文字，不增删章节/SVG；结构计数 140 章 / 418 图 / 411 SVG / 247 grounds 不变，内容指纹按预期更新并重新 freeze。
